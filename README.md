# Watermark_remover

檢測並消除 AI（Claude 等）生成之 Word（.docx）檔中的隱藏痕跡。

> **先看這一點：本工具做的是「可疑度偵測」，不是「是 AI／不是 AI」的二分法。**
> 沒有任何一個訊號能單獨證明一份文件由 AI 產生，也沒有任何一個訊號能單獨證明它不是。工具對每個發現給出的是**嚴重度或信心等級（高／中／低）**，並統計數量、標出位置，由你判斷。報告中**沒有**「這份文件 X% 是 AI」這種數字。詳見 [偵測的本質：可疑度，不是二分法](#偵測的本質可疑度不是二分法)。

> **核心原則**：AI 只參與「想怎麼改」；真正產出最終檔案的步驟（重建、寫回、改作者／公司屬性）全部是**純本地、確定性的 Python 腳本**，不呼叫任何 AI。網站本身完全不連到 AI；要請 Claude 提改寫建議時，由你自己把待修版交給 Claude desktop。

## 看病流程：跟著網頁走一遍

網頁介面是一間卡通的「輔大醫院」。你的 Word 檔是病人，AI 痕跡是病情，整個使用過程就是一次就診，共七站，每走完一站鏡頭會自動向左平移到下一個場景。**你不需要操控人物，只要在每一站做該做的事。**

| 站 | 情節 | 你實際要做的事 |
|---|---|---|
| 1 掛號 | 掛號櫃檯高高在上、窗口小小的，病人個子矮，要踮腳把病歷遞進去。叫號機與掛號單顯示 `414155039` | 把 .docx **用滑鼠拖進視窗**（或點一下窗口選檔）。病人的手臂會拿著文件跟著游標走，放開就遞進窗口並蓋「已收件」章 。已經有改好的待修版時，可點旁邊的「收費處／藥局」指示牌，直接跳到第 6 站（設定自動帶入，不需重新掛號）|
| 2 檢測 | 病人躺上電腦斷層（CT）掃描。**整體風險高**：病人當場暈倒；**最高只有中**：當場坐上輪椅；**只有低**：長出一口氣 | 看結果摘要（檔案層高／中／低、文字層可疑部位前三名）。可點「查看檢測詳情」或「完整報告」，確認後按「繼續」 |
| 3 手術同意書 | 診療室（樹德樓 LW210），廖醫師說明手術內容，病人簽名同意後才進手術室；同意書就是設定表單 | 選是否**啟用文字風格層**、是否**保留隱藏文字**，並填最終檔的**作者／公司**（留空用預設），**勾選同意**後才能繼續。這些設定會記在瀏覽器（`localStorage`），下次自動帶入；同意本身不記 |
| 4 治療 | 醫師當場治療。**高風險**：心肺復甦搶救；**中**：卡通式截肢一條腿（無血腥）；**低**：護理師過來往屁股打一針。治療完病人**改坐輪椅，直到結束** | 等清理完成。病歷會列出四項檢查：白名單重建、改寫作者與公司、複掃痕跡、與原檔格式比對 |
| 5 處方 | 護理師從印表機印出處方箋 | 產生並下載**待修版**（在需要人工處理的段落加上 Word 註解，作者為「檢測提示」）。用 Word 開啟，**審閱 → 下一則**逐一修改後存檔。處方箋底部有一段小字提示詞，可複製後連同待修版交給 Claude desktop 請它逐則提出改寫建議（網站不代為送出）。沒有需人工處理的段落時會自動跳過這一站 |
| 6 繳費 | 收費窗口，同樣是小窗口；旁邊有一台信用卡 POS 機 | 把**改好的待修版**拖進窗口（或選擇「不需人工修改」跳過），再**按 POS 機的綠色「確認」鍵**，才會產生最終乾淨版 |
| 7 領藥 | 藥師從領藥處遞出藥袋 | 下載**最終乾淨版**。頁面會顯示複掃結果、格式比對、已移除的工具註解數量，以及文字層仍存在的可疑部位數。可再「再掛一個號」處理下一份 |

幾點對照說明：

- **「高／中／低風險」怎麼算**：取「檔案層嚴重度」與「文字層信心等級」兩者的最高值。這只用來決定劇情與排序，**不是機率，也不是判定這份文件是不是 AI 寫的**。
- **待修版不能繳交**：它是工作副本，裡面有「檢測提示」註解。第 6 站交回去之後，工具會把這些註解整批移除，最終版才是要繳交的。你自己文件裡原本的註解不受影響。
- **風格層**只做規則式、保守的替換；真正有效的內容層改寫，需要你在 Word 裡依註解自己修（見下方「命令列用法」的 `export` / `apply`）。
- 頁面為桌面版，設計成一頁看完，不需要捲動。

## 同學本地部署

在自己的電腦跑一份，文件不會離開你的電腦。需要 **Python 3.9 以上**與 **git**。

> 本 repo 為**私有**。請先向作者取得存取權限（被邀請為協作者），或直接向作者要原始碼壓縮檔，解壓後從 `cd` 那一步開始。

**macOS／Linux**
```bash
git clone https://github.com/hsiliang/Watermark_remover.git
cd Watermark_remover
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python3 -m wmr web
```

**Windows（PowerShell）**
```powershell
git clone https://github.com/hsiliang/Watermark_remover.git
cd Watermark_remover
py -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
py -m wmr web
```

看到「網頁介面：http://127.0.0.1:8765/」後，用瀏覽器開啟該網址。**保持終端機視窗開著**，按 Ctrl+C 結束。

| 想做的事 | 指令 |
|---|---|
| 換埠（8765 被占用時） | `python3 -m wmr web --port 9000` |
| 更新到最新版 | 在專案資料夾執行 `git pull`，然後重新啟動 |
| 不開網頁、只用命令列 | `python3 -m wmr clean 原檔.docx -o out/乾淨.docx --style --review` |
| 跑測試 | `pip install -r requirements-dev.txt` 後 `python3 -m pytest -q` |

注意：
- Windows 的指令我沒有實際測試過；macOS 上用乾淨的 clone 驗證過（Python 3.9.6、`requirements.txt` 安裝，頁面回應正常）。
- **不要**把 `--host` 改成 `0.0.0.0` 對外開放，除非先設定環境變數 `WMR_PASSWORD`（共用密碼）。預設只綁本機是刻意的。
- 上傳的文件暫存在 `out/web/`，每次啟動會清空。
- 若設了 `WMR_TTL_MIN`（部署預設 240＝4 小時），暫存從**最後一次操作**起算，閒置超過才會清除；每次存取都會續期。關掉網頁後，只要手上有改好的待修版，從首頁「收費處／藥局」就能接續完成，不需要暫存還在。
- Word 重存（`--word`、`--page-check`）只適用於 Mac 版 Word；LibreOffice 渲染比對（`--render-check`）需另外安裝 LibreOffice。這兩項都是選用。

## 它能做什麼

| 功能 | 說明 | 是否用 AI |
|---|---|---|
| **檔案層檢測** | 掃描 zip 結構、套件部件、文件屬性、XML 殘留、隱藏文字、rsid／paraId 等痕跡 | 否 |
| **白名單重建** | 只保留文件必要部件，丟棄 customXml、縮圖、舊 app／core 屬性，剝除 rsid、proofErr、書籤殘留、圖片 metadata，並重排成 Word 風格的 zip | 否 |
| **屬性改寫** | 作者／最後修改者、公司（預設 `Hsi Liang`／`https://github.com/hsiliang`，網頁與 `--author`／`--company` 皆可改；最後一步，純本地） | 否 |
| **文字風格層**（選用） | 規則／詞表式：殘留標記、套話刪除、慣用語替換、兩岸用語、Markdown 殘留、emoji、破折號、標點 | 否 |
| **可疑部位報告** | 統計各類 AI 文風訊號（句長均勻、否定排比、模糊引用…）並標出位置，供**人工**判斷與修改 | 否 |
| **匯出／寫回改寫** | 把可疑段落匯出成 JSON，交給 AI 或自己改寫，再**純本地**寫回，保留格式 | 改寫由你決定；寫回否 |
| **格式保真驗證** | 逐字元比對格式，並可用 LibreOffice 渲染逐頁比對畫面 | 否 |
| **網頁介面** | 本機瀏覽器操作：上傳 → 檢測 → 清理 → 下載 | 預設否 |

## 安裝

需要：macOS／Linux、Python 3.9 以上。

```bash
cd Watermark_remover
python3 -m venv .venv && source .venv/bin/activate     # 建議使用虛擬環境
pip install -r requirements-dev.txt     # 只跑網頁／清理用 requirements.txt 即可；--render-check 與測試需要 dev 版
```

選用的外部軟體：

| 軟體 | 用在哪 | 沒有的話 |
|---|---|---|
| LibreOffice | `--render-check` 逐頁畫面比對 | 其他功能不受影響 |
| Word for Mac | `--word`、`--page-check`（選用） | 其他功能不受影響 |

驗證安裝：

```bash
python3 -m pytest -q          # 應全部通過
```

## 快速開始

最常用的一行（清理 + 風格層 + 報告 + 畫面比對）：

```bash
python3 -m wmr clean 論文.docx -o out/乾淨.docx --style --review --render-check
```

這會依序：掃描原檔 → 白名單重建 → 改作者／公司 → 複掃 → 保真比對 → 產生可疑部位報告與標註副本。
輸出在 `out/` 資料夾。**請用 `out/乾淨.docx` 繳交；`*_標註.docx` 只供檢閱，不要繳交。**

## 網頁介面

```bash
python3 -m wmr web                 # 預設埠 8765
python3 -m wmr web --port 9000     # 指定埠
```

看到「http://127.0.0.1:8765/」後，**保持該終端機視窗開著**（按 Ctrl+C 即結束），用瀏覽器開啟網址。修改 `wmr/static/index.html` 後需**重啟**伺服器才會生效。

介面是「輔大醫院」：2D 橫向捲軸的卡通醫院，共 7 個場景，每完成一步鏡頭自動由右向左平移，不需要操控人物。頂端進度條顯示目前步驟，不可跳步。

| 場景 | 做什麼 | 演出 |
|---|---|---|
| 1 掛號 | 把原始 .docx 拖進視窗（或點窗口選檔）提交 | 櫃檯很高、窗口很小、病人很矮；病人的手臂拿著文件跟著滑鼠移動，放開後遞進窗口並蓋「已收件」章 |
| 2 檢測 | 顯示檔案層高／中／低與文字層可疑部位；可看詳情與完整報告 | CT 掃描；整體風險高→病人暈倒、最高為中→坐輪椅、只有低→鬆一口氣 |
| 3 手術同意書 | 設定風格層、保留隱藏文字、最終檔作者與公司（預設 `Hsi Liang`／`https://github.com/hsiliang`，留空用預設） | 醫生向護理師交代任務 |
| 4 治療 | 白名單重建 → 改屬性 → 複掃 → 與原檔格式比對 | 高→心肺復甦、中→卡通截肢一條腿、低→護理師打針（皆為卡通風格，無血腥） |
| 5 處方 | 產生**待修版**（在需人工處理的段落加 Word 註解），可下載 | 護理師從印表機印出處方 |
| 6 繳費 | 提交在 Word 修改後的待修版（或選擇跳過），按 POS 機「確認」觸發最終乾淨版 | 收費窗口＋信用卡 POS 機 |
| 7 領藥 | 下載最終乾淨版；可看複掃與格式比對詳情 | 藥師遞出藥袋；「再掛一個號」重置 |

「整體風險」＝檔案層嚴重度與文字層信心**取最高**，只是為了決定演出與排序的啟發式，不是機率，也不是「是不是 AI」的判決。

若待修版沒有任何需要人工處理的段落，場景 5 會自動前往場景 6（跳過人工修改，直接繳費）。場景 7 的「文字層可疑部位」列出清理後文字層仍存在的旗標數，僅供參考，不是判決。

**待修版**是工作副本（註解作者為「檢測提示」），**不可直接繳交**。在 Word 用「審閱 → 下一則」逐一修改後存檔，再於場景 6 提交；最終版重建時會把這些註解整批移除。你自己原本文件裡的註解不受影響。

其他：
- `?demo=<場景1-7>[:high|medium|low]`（例如 `?demo=2:high`）用假資料直接預覽場景，不呼叫後端；`?demo=1:drag`、`?demo=6:skip` 為特殊狀態。
- 只綁 `127.0.0.1`，拒絕 Host 不是 localhost／127.0.0.1 的請求（防 DNS rebinding）。**程式沒有登入或認證機制**；若日後要架成可從網路連入的網站，必須先加上認證與傳輸加密，不能直接改綁其他位址。
- 網頁不含：Word 重存、LibreOffice 渲染比對、匯出／寫回改寫。這些請用命令列。
- 暫存檔放在 `out/web/<id>/`（含上傳的文件），每次啟動會清空；`--keep` 可保留。
- 頁面為單一自包含檔案（`wmr/static/index.html`，無外部資源）。

## 命令列用法

所有指令都是 `python3 -m wmr <子指令>`。

### `scan` — 只檢測，不修改
```bash
python3 -m wmr scan 檔案.docx            # 檔案層痕跡
python3 -m wmr scan 檔案.docx --style    # 一併檢測文字風格痕跡
python3 -m wmr scan 檔案.docx --json     # JSON 輸出
```
發現高嚴重度項目時結束碼為 1。

### `clean` — 清理（主要指令）
```bash
python3 -m wmr clean 原檔.docx -o out/乾淨.docx [選項]
```

| 選項 | 說明 |
|---|---|
| `--style` | 啟用文字風格層（規則式，選用）；會印出變更日誌 |
| `--style-rules 群組,群組` | 指定風格群組，可用：`artefact, filler, lexicon, region, markdown, emoji, dash, punct, quotes`（`quotes` 預設關） |
| `--review` | 清理後產生可疑部位 HTML 報告與標註副本 |
| `--render-check` | 用 LibreOffice 渲染原檔與輸出，逐頁比對畫面（格式保真的最直接證據） |
| `--keep-hidden` | 不刪除隱藏文字 |
| `--author 名稱` | 最終檔的作者與最後修改者（預設 `Hsi Liang`） |
| `--company 名稱` | 最終檔的公司（預設 `https://github.com/hsiliang`） |
| `--word` | 再用 Word for Mac 重存一次（**選用，不建議預設使用**，見下方警告） |
| `--page-check` | 用 Word 重存原檔與輸出，比對 Word 計算的頁數／字數 |

> **關於 `--word`**：Word 重存會改寫樣式定義。在真實論文上實測，LibreOffice 渲染結果與原檔不同（58 頁對 56 頁），所以預設不用；若要用，請務必搭配 `--render-check`。
> 本機 Word 的「另存新檔」不可用，改採「開啟 → 標記已修改 → 關閉並儲存」。這會彈出 Word 視窗，可能需要你在場確認。

**風格層的套話刪除規則**：「綜上所述」「總而言之」「總的來說」「值得注意的是」等，只在**句首或逗號後、後面接逗號、且不在引號內**時才刪除，否則不動，避免留下殘句或改到引文。「綜上所述——」這種破折號寫法不會觸發。

### `review` — 可疑部位報告
有些訊號像 AI，但**不確定、也不該由 AI 自動改寫**（句長均勻、否定排比、模糊引用、連接詞密集…）。這些只統計並標出位置，交給你判斷。

```bash
python3 -m wmr review 檔案.docx                                  # 產生 HTML 報告
python3 -m wmr review 檔案.docx --annotate out/檔案_標註.docx    # 另產生有色標註副本
python3 -m wmr review 檔案.docx --json out/report.json           # 另存 JSON
python3 -m wmr review 檔案.docx --skip-heading 附錄               # 再略過「附錄」章節（可重複）
```

- **HTML 報告**：各類型數量（含信心等級、可否自動修）、熱點段落、章節＋第幾段、**可點擊複製的 Word 搜尋字串**（貼進 Word 的「尋找」即可定位）。
- **標註副本**：在可疑處加螢光筆，並自動避開文件原本就有的螢光筆顏色。**僅供檢閱，勿繳交。**
- 自動略過「參考文獻／參考資料／References／Bibliography」章節。
- 文件層級指標包含句長變異、連接詞開頭比例、「的」字密度、逗號密度、括號密度、破折號數、「具體資訊稀少的段落比例」等。括號密度只供參考，**未設門檻**（沒有資料可判斷多少算偏低）。

### `export` / `apply` — AI／人工改寫，純本地寫回
真正可能影響統計性檢測的是**內容層改寫**（句型、節奏、論述），這件事腳本做不到，需要人或 AI。工具負責「把要改的段落交出去」與「把改好的結果寫回來」。

```bash
# 1. 匯出有可疑訊號的段落（附各段問題與改寫指引）
python3 -m wmr export 稿.docx -o edits.json [--min-conf 低|中|高]

# 2. 把 edits.json 交給 Claude 或自己改：在每項的 new_text 填入改寫，不改的保持 null

# 3. 純本地寫回，保留段落與字元格式
python3 -m wmr apply 稿.docx edits.json -o 稿_改.docx

# 4. 最後的重建＋改屬性
python3 -m wmr clean 稿_改.docx -o out/最終.docx --style --review
```

- `--min-conf 中`／`高`：只匯出中／高信心的段落（實驗中，優先改這些最划算）。
- 含圖片、欄位（目錄／交互參照）、註腳、超連結、公式的段落標為 `editable: false`，請在 Word 手動修改。
- 匯出後若原稿被改動，該段會因「原文不符」被略過，不會誤改。
- `new_text` 可用 `**粗體**` 標記。
- `apply` 加 `--force` 可強制替換含超連結／欄位的段落（可能破壞該段結構，慎用）。
- 改寫時不要新增原文沒有的事實、數據或來源；「模糊引用」的問題 AI 無法憑空補出處，請人工處理。

## 建議工作流程

**情境 A：只想清掉檔案層痕跡（格式零風險）**
```bash
python3 -m wmr clean 原檔.docx -o out/乾淨.docx --render-check
```
確認輸出為「渲染比對：一致」、複掃「未發現痕跡」，再用 Word 打開目視一次。

**情境 B：連文字風格也處理，並找出要人工修改的地方**
```bash
python3 -m wmr clean 原檔.docx -o out/乾淨.docx --style --review
```
打開 `out/乾淨_review.html`，依「信心：高／中」的類型優先處理，用報告上的搜尋字串在 Word 裡定位並修改。

**情境 C：大量改寫（AI 輔助）**
1. `export`（建議 `--min-conf 中`）→ 交給 AI 或自己改寫 → `apply`
2. 對 `apply` 的輸出再跑 `clean ... --style --review`（確保最後一步是純本地腳本、屬性正確）
3. 用 `review` 檢查剩餘的可疑部位，人工補強

**最後務必**：
- 用 Word 開啟成品，目視確認版面；
- 到「檔案 → 資訊」確認作者與公司；
- 繳交的是 `clean` 的輸出，不是 `_標註.docx`。

## 痕跡分哪幾層

AI 生成的 Word 檔，痕跡不只在「文字內容」，而是**由外到內共六層**。層次越外越容易被程式確定性地處理，越內越只能給出可疑度。

| 層 | 例子 | 性質 | 工具的處理 |
|---|---|---|---|
| 1. zip／封包結構 | 產生器（如 docx-js）特有的 zip 檔案順序、目錄項、時間戳、`create_system`、單引號 XML 宣告、空 rels、雜湊命名的圖片檔 | 確定性特徵 | 重建時改成 Word 的樣子 |
| 2. 文件屬性 | 作者、最後修改者、公司、應用程式名稱、標題、描述、縮圖、`customXml` | 確定性特徵 | 丟棄舊的，重寫為你指定的作者／公司（預設 `Hsi Liang`／`https://github.com/hsiliang`） |
| 3. XML 殘留 | `rsid*`、`paraId`、`proofErr`、`_GoBack` 書籤、設定檔中的 rsid 清單 | 確定性特徵 | 剝除 |
| 4. 內容中的隱形東西 | 隱藏文字（`w:vanish`）、1pt 以下字級、白色文字、零寬／bidi／tag 字元、特殊空白、圖片 EXIF／PNG metadata、註解作者 | 確定性特徵 | 刪除或清除 |
| 5. 文字殘留與機械風格 | `contentReference[oaicite:…]`、`utm_source=chatgpt.com`、Markdown 符號（`**`、`#`）、emoji、破折號、簡體字混入、兩岸用語混用、套話與慣用語 | 多半是明確的字串，但**不是每個都能證明 AI** | 風格層（選用）規則式處理；其餘列入報告 |
| 6. 文風與結構統計 | 句長過於均勻、否定排比、三項並列、首尾三段式、模糊引用、連接詞密集、章節總是三個小節、內容空泛… | **純機率性，人類寫作也會出現** | **只統計與標位置，交人工判斷**；可匯出給 AI／人改寫 |

第 1～4 層是**檔案本身的事實**（有或沒有），工具可以放心地確定性處理。第 5 層介於兩者之間。第 6 層則完全是**可疑度**：即使報告標了很多處，也不能說「這是 AI 寫的」，只能說「這些地方的寫法在 AI 文本中較常見」。

## 我如何偵測、如何修改

### 偵測

**檔案層（第 1～4 層）：`scan`**
逐一檢查 zip 結構、`[Content_Types].xml`、各部件、`core.xml`／`app.xml`、`document.xml` 等 XML，比對一份「已知產生器特徵」清單（例如 docx-js 的單引號 XML 宣告、`rsid`、`paraId`、雜湊命名圖片、非 1980 的 zip 時間戳）。每項發現附**嚴重度**：

- `high`：幾乎只有自動產生器或刻意藏東西才會有（隱藏文字、應用程式簽章、外來註解作者、零寬字元…）
- `medium`：可疑，但人工處理過的文件也可能出現
- `low`：產生器常見，但正常 Word 檔也可能有（如 rsid）

**文字層（第 5～6 層）：`review`**
`suspect.py` 對每個段落套用約 25 類規則，每類有固定的**信心等級**（高／中／低）與**可否自動修**。大致分三種：

1. **字串型**：用正規表達式與詞表找（殘留標記、套話、慣用語、兩岸用語、簡體字、Markdown 符號…）。
2. **結構型**：看句式或排版（否定排比「不是…而是…」、「首先／其次／最後」、三項並列、段尾總結句、粗體標籤開頭、標題公式、章節總是三個小節、連續段落開頭雷同…）。
3. **統計型**：以**本文自己的分布**為基準，而非絕對門檻。例如「句長過於均勻」是看該段的句長變異係數是否落在**全文最低的 20%**（且低於 0.45）；表格內文字與文獻清單（含多筆「作者（年）。」或過半句子帶年份／文獻編號）不列入，因為那不是文章的句子；「的字密度」「連接詞開頭比例」等同理。這樣同一套規則能適用於不同文體。

另有幾項**文件層級指標**只供參考、不設門檻：句長平均／標準差、段落長度變異、連接詞開頭比例、每百字的「的」／逗號／括號、破折號數，以及「具體資訊稀少的段落比例」。

**熱點段落**：每個旗標依信心給權重（高 3／中 2／低 1），同一段的旗標加總，取前 25 段列為熱點，方便你先處理最值得看的地方。這是**排序工具**，不是機率。

### 修改

| 方式 | 適用 | 是否用 AI | 風險 |
|---|---|---|---|
| **白名單重建**（`clean`） | 第 1～4 層 | 否 | 低；用逐字元格式比對與 LibreOffice 逐頁渲染驗證 |
| **風格層**（`clean --style`） | 第 5 層的明確字串 | 否 | 中；規則式，已採保守策略（見下） |
| **人工修改** | 第 6 層 | 否 | 無；依報告的 Word 搜尋字串定位 |
| **匯出／寫回**（`export`／`apply`） | 第 6 層，想大量改寫時 | **改寫由 AI 或你做**；寫回是純本地 | 中；只改有旗標的段落，原文不符則略過 |

**重建怎麼做**：不是「在原檔上修補」，而是把內容與可見格式搬到一個**全新的封包**，只搬白名單內的部件，再用 Word 的順序、時間戳與屬性重寫。這樣舊檔的產生器痕跡不會殘留。最後一步（`finalize`）改作者／公司，也是純本地腳本。

**風格層的保守策略**：寧可漏掉，也不改壞句子。例如：
- 套話（「綜上所述」「值得注意的是」…）只在**句首或逗號後、後面接逗號、不在引號內**才刪。
- 標點只看漢字鄰接，不動公式括號。
- 兩岸用語只換有明確對應的詞；「網絡」「調用」「激活」在台灣也有正確用法，所以不換。
- 參考文獻章節整段略過。
- 同一個詞有多個替代選項時輪替使用，避免製造新的單調。

**機械式替換對統計性檢測幾乎沒用**：實驗中，風格層對檢測器分數的影響很小。真正有改善的是第 6 層的內容改寫（句型、節奏、論述），這需要人或 AI 來做，所以才有 `export`／`apply`。見 [`docs/experiments.md`](docs/experiments.md)。

## 偵測的本質：可疑度，不是二分法

**請不要把報告當成「AI 判決書」。** 理由：

1. **沒有單一訊號是決定性的。** 「首先／其次／最後」、破折號、三項並列、「的」字偏多，人類寫作也常見。一項旗標只是「這裡有點像」。
2. **用等級，不用機率。** 每類旗標只有高／中／低的信心，是我依資料來源強度（見 [`docs/research-notes.md`](docs/research-notes.md)）人工設定的，**不是量測出來的機率**。我沒有人工標註的人類／AI 語料，無法算每類旗標的精確率與召回率。
3. **同一個訊號，不同文體意義不同。** 規範性的學術論文本來就句式工整、連接詞多、少用口語，容易被標得多；這不代表它是 AI 寫的。反過來，沒有被標出來也不代表安全。
4. **統計型旗標是相對的。** 「句長過於均勻」是「本文裡相對最均勻的 20%」，所以任何文件都會有一些段落被標出來，數量多寡本身不代表什麼。
5. **多項訊號疊加才較有意義。** 熱點段落的分數把同段的旗標加總，是為了讓你「先看哪裡」，而不是「判定哪裡是 AI」。
6. **外部檢測器本身也是機率性的。** 實驗用的開源檢測器會把人類寫的維基百科判成 AI；各商業平台對同一篇文章的結果也差異極大。所以本工具只能協助你**降低可疑度、找出可疑處**，無法保證任何平台的判定結果。

因此報告的用法是：**看各類旗標的數量與分布，優先處理高／中信心的段落，用人的判斷決定要不要改。** 「需人工」的類型，工具刻意不自動修改。

## 驗證與已知限制

**已驗證（真實 Claude／docx-js 產物，78 頁論文計畫書）**
- 本地重建：LibreOffice 渲染 56／56 頁與原檔逐頁相同；掃描器零發現；Word 能開啟。
- 加上 `--word`：Word 自算頁數／字數與原檔相同（78 頁、10,597 字），但 LibreOffice 渲染變成 58 頁、每頁皆有差異。
- 網頁介面：在真實論文上完整跑過上傳、清理、下載。

**限制（請如實看待）**
- **未跑過任何商業檢測網站**（知網、維普、朱雀、GPTZero 等）：它們需要登入、驗證碼或付費。請用學校指定的平台自行測試，這是最直接的證據。
- 可疑部位的**精確率／召回率沒有量測**（沒有人工標註的人類／AI 語料）。
- 掃描器反映的是我的假設，**不等於同學的偵測系統**。
- 獨立檢測器實驗樣本很小（3 篇生成文章＋1 份真實論文，長度 5,500～8,000 字），且生成與改寫皆同一模型；機械式 `--style` 對統計性檢測分數幾乎沒有影響，AI 輔助改寫有效但不均勻。詳見 [`docs/experiments.md`](docs/experiments.md)。
- 「補具體事實可降低分數」的假說在小規模實驗中**不成立**，工具的建議文字已據此改寫。
- 風格層是規則式，仍可能有漏刪與誤判；刪除套話採保守策略，寧可漏掉也不改壞句子。
- 本機 Word 的 `save as` 不可用，`--word` 改用「開啟 → 標記已修改 → close saving yes」。

## 常見問題

**瀏覽器打不開網頁？**
確認執行 `python3 -m wmr web` 的終端機視窗仍開著、沒按 Ctrl+C；網址要完整輸入 `http://127.0.0.1:8765/`（不是 https）。埠被占用時改用 `--port`。

**清理後 Word 版面跑掉？**
先不要用 `--word`。用 `--render-check` 確認渲染一致；若不一致，請把檔案與輸出差異頁告訴我。

**風格層把某個詞改錯了？**
用 `--style-rules` 只開需要的群組（例如不要 `lexicon`），並檢查 `clean` 印出的「風格層變更日誌」。

**為什麼不直接讓 AI 輸出最終檔？**
本專案的規則：最終檔必須由非 AI 的本地腳本產生，避免留下生成痕跡。AI 只提供改寫文字，由 `apply` 與 `clean` 寫進文件。
